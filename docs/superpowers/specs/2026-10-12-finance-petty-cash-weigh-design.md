## 2. สิ่งที่พบ แล้วกระทบ spec

### 2.1 ใบเบิก 1 ใบ มีหลายรายการ ไม่ใช่ยอดเดียว

spec ฉบับแรกตั้ง `fin_petty_claims.amount` เป็นยอดเดียวต่อใบ **ซึ่งใช้ไม่ได้กับของจริง**
ใบจริงรวม 16 คัน 3 ราคา ไว้ในใบเดียว → ต้องมีตารางลูก `fin_petty_claim_items`

### 2.2 ใบครอบ "ช่วงวัน" ไม่ใช่วันเดียว

ใบสำคัญจ่ายลงวันที่ 25/9 แต่ค่าใช้จ่ายจริงเกิดระหว่าง **17–24/9**
→ หัวใบต้องมี `period_from` / `period_to` และรายการลูกถือ **วันที่ชั่งของตัวเอง**
ใบรับรองแทนใบเสร็จพิมพ์ช่วงวันนี้ลงในประโยครับรองโดยตรง

### 2.3 ของจริงมีข้อมูลซ้ำอยู่แล้ว — และเลขที่บัตรชั่งคือตัวตัดสิน

หมายเหตุบรรทัดแรกเขียนทะเบียน **1093 สองครั้ง** ในใบเดียว
อาจเป็นการชั่ง 2 เที่ยวจริง หรืออาจเขียนผิด — **ด้วยกระดาษแยกไม่ออก**

เลขที่บัตรชั่งแยกออก เพราะมันคือตัวระบุ *เหตุการณ์ชั่งหนึ่งครั้ง* ไม่ใช่สัญญาณอ้อมแบบวันที่+ทะเบียน

| 1093 สองแถว | แปลว่า | ระบบทำ |
|---|---|---|
| เลขบัตรต่างกัน | ชั่งจริง 2 เที่ยว | ผ่าน (เตือนอ่อนจาก วันที่+รถ ให้ยืนยัน) |
| เลขบัตรเดียวกัน + รถคันเดียวกัน | เบิกซ้ำ | **บล็อก** |

→ ด่านซ้ำจึงมี **สองระดับ**: เลขบัตรชั่ง+รถ = บล็อก · วันที่+รถ = เตือน
และทั้งคู่ทำงาน **ระดับรายการ ไม่ใช่ระดับใบ**

**คีย์ของด่านเข้ม = เลขที่บัตรชั่ง + เบอร์รถ + ทะเบียนรถ** ครบทั้งสามค่าถึงนับว่าซ้ำ

เลขบนใบจริงเป็นเลขรันสั้น (000055 / 000061 / 000172) ถ้าแต่ละลานชั่งรันเลขของตัวเอง
เลขเดียวกันจะโผล่จากหลายลานได้ — แต่การใส่รถเข้าไปในคีย์ปิดช่องนั้นไปเอง
เพราะบัตรเลขเดียวกันจากลานอื่นย่อมเป็นรถคนละคัน จึงเป็น **บล็อกจริง ไม่มีทับ**
ไม่ต้องเพิ่มช่องลานชั่งเพื่อการนี้

ผลพลอยได้: ทะเบียนที่กรอกต้องเป็นของเบอร์รถนั้นจริง ระบบเติมทะเบียนจาก master
ให้อัตโนมัติเมื่อเลือกเบอร์รถ (ดู §2.5) คีย์จึงเชื่อถือได้ไม่ขึ้นกับว่าใครพิมพ์

### 2.4 ราคาไม่คงที่ และผูกกับประเภทรถ

100 / 120 / 80 บาท ปนในใบเดียว และ 100 บาทมีทั้งโม่ใหญ่และโม่เล็ก
→ `rate` เป็นค่าที่กรอกต่อรายการ **ไม่ใช่ค่าคงที่ในระบบ** ส่วน `truck_type` เก็บแยกเพื่อออกรายงาน

### 2.5 ทะเบียนบนใบเป็นเลขข้างรถ ไม่ใช่ทะเบียนราชการ

"161, 144, F014, 1126, 340" คือรหัสรถภายใน ส่วนใบชั่งของลานชั่งเขียน "71-4285", "71-4728"
→ ช่องเลือกรถต้องค้นได้ทั้ง **รหัสรถภายใน** และ **ทะเบียน** แล้วเก็บทั้งคู่ลงฐาน

**กติกาที่ต้องมี**

1. **กรอกเลขแล้วเช็คทันที** — ไม่เจอใน Mongo ขึ้นเตือน "ยังไม่พบใน ATMS อาจรอ sync"
   แต่ **ไม่บล็อก** เพราะ v5 sync รอบ 4 ชม. (เดือนปัจจุบัน 08:30/12:30/16:30/20:30)
   ใบที่เพิ่งเปิดใน ATMS จะยังไม่มาถึง
2. **ยอดต้องตรงกัน** — ผลรวม `ยอดเงิน` ของทุกแถวใน DD เทียบกับยอดรวมของใบเบิก
   ไม่ตรง = **เตือนทั้งเจ้าหน้าที่และผู้อนุมัติ** พร้อมแสดงส่วนต่าง (นี่คือด่านที่กระดาษไม่มี)
3. **อ่านอย่างเดียว** — ระบบไม่เขียนอะไรกลับไปที่ `stockmovement_v5` เลย
   DD เป็นของ ATMS ค่าในนั้นคือค่าจริง
4. **เก็บ snapshot ตอนปริ้น** — บันทึกแถวที่ดึงมาไว้ใน `fin_petty_claims.dd_snapshot` (jsonb)
   เพื่อให้ใบที่ปริ้นแล้วไม่เปลี่ยนตามที่ ATMS แก้ย้อนหลัง (ATMS แก้ย้อนได้ ~2 เดือน)
5. **แคช** — อ่านซ้ำใช้ snapshot ไม่ยิง Mongo ใหม่ · ปุ่ม "ดึงใหม่" ให้กดเองได้

**ที่ต้องเตรียมฝั่งฐานข้อมูล** — ยังไม่มี index บนฟิลด์ `DD` ต้องสร้าง
`db.stockmovement_v5.createIndex({DD: 1})` ก่อนเปิดใช้ ไม่งั้นทุกครั้งที่กรอกเลข
จะสแกน 435k แถวบน cluster ที่ cache แค่ ~370MB

## 9. ยังต้องถาม

1. **Project Code** บนใบสำคัญจ่าย ใช้เมื่อไร ใครกรอก (ตัวอย่างเว้นว่าง)
